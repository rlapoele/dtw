# Increment 003: color-engine options comparison

8 November 2026 — **Assessment and recommendation; no selection or implementation.** Read-only source research, plus this document, at clean `dev` baseline `3fef603cd8c5a0ae2cc767f670a9c23c8f07fffa`. The [agreed contract](003-visible-color-authoring.md), [full numerical policy](003-color-policy-proposal.md) and [architecture](../project/architecture.md#domain-engine) remain authoritative. No probes, installs, dependency changes, builds or application/prototype edits were performed for this comparison.

## Recommendation

**User clarification incorporated — 8 November 2026:** color mixing and gradient calculation are confirmed future product needs. They remain outside Increment 003 implementation/acceptance, but their long-term cost must count in this decision. Interpolation policy, gradient scope, API and timing remain unresolved; this clarification does not adopt a library's defaults.

**Prefer retaining an upstream manipulation backend behind DTW's policy boundary as the long-term direction to validate.** A unified backend for conversion and future manipulation could reduce duplicated numerical behavior, standards tracking and specialist maintenance. Culori deserves the first comparison run: its raw polar path avoids Color.js's known epsilon and its positioned multi-stop interpolation is directly relevant. This is structural fit, not a numerical winner or selection; Color.js retains useful measured evidence and capable interpolation APIs.

Under the retained all-intermediate guard constraint, a **narrow owned five-space module has the clearest immediate observability fit**: it can expose actual stages and place checks before dependent operations. Neither stock library conversion API demonstrates that refusal contract. If library reuse cannot satisfy it, pair a narrow strict kernel with upstream manipulation only after specifying their consistency boundary. Ownership of equations alone does not solve nonlinear uncertainty, and owning conversion does not make owning all manipulation the economical next step.

Do not choose a full owned manipulation library now. Its real future value is acknowledged; its additional standards, interpolation/gradient edge cases and expertise burden are not shown to outweigh reuse. Prefer unified upstream reuse if its verified policy adapter stays small; prefer a bounded owned kernel over a large conversion fork if necessary. Reassess full ownership only if the future agreed behavior requires pervasive upstream replacements. No agreed guard or no-mapping rule is relaxed to obtain that recommendation.

## Precision and extensibility

Both inspected backends use JavaScript Number arithmetic and native Math functions, not arbitrary-precision decimal transforms. Culori's [linear-RGB→OKLAB](https://github.com/Evercoder/culori/blob/v4.0.2/src/oklab/convertLrgbToOklab.js) embeds matrix sums inside `Math.cbrt`; its [transfer function](https://github.com/Evercoder/culori/blob/v4.0.2/src/lrgb/convertRgbToLrgb.js) uses `Math.pow`. Installed Color.js's [OKLAB source](https://github.com/color-js/color.js/blob/v0.7.1/src/spaces/oklab.js) similarly uses numeric matrices and `Math.cbrt`. A Decimal wrapper before/after these calls does not improve their internal precision or reveal their intermediate errors.

Color.js [ColorSpace](https://github.com/color-js/color.js/blob/v0.7.1/src/ColorSpace.js) accepts `fromBase`/`toBase` transforms; its [RGBColorSpace](https://github.com/color-js/color.js/blob/v0.7.1/src/RGBColorSpace.js) exposes RGB↔XYZ matrices and named modules such as OKLAB expose their own constants. Culori [useMode](https://github.com/Evercoder/culori/blob/v4.0.2/src/modes.js) accepts custom conversion functions, while its [functional entry point](https://github.com/Evercoder/culori/blob/v4.0.2/src/index-fn.js) exposes low-level converters. These are real extension points, but **neither is a plug-in arithmetic backend for inspected built-in transforms**. New transforms must implement their own arithmetic. Replacing global built-in modes/spaces adds registry coupling; a private narrow route is easier to audit than mutating shared defaults.

Low-level composition can expose returned linear/rectangular coordinates without a fork, but cannot observe inline LMS operands or native Math internals. Calling built-in `fromBase` or low-level Culori functions does not automatically close this gap. Guard inventory must identify the stages actually used, and cancellation checks must distinguish necessary loss from conservative refusal. The proposed named-stage interpretation and automatic cbrt-collision refusal remain **unagreed**; do not charge either library for implementing every scalar/native internal guard as though that stronger interpretation were settled. Equally, do not silently narrow the agreed requirement to endpoints to make a wrapper pass.

A hybrid could keep exact identity/byte math plus ordinary binary transforms and use owned higher-precision hotspots or fallback for demonstrated cancellation. It only helps if the fallback receives exact source data and higher-precision coefficients before loss, and covers the relevant transfer, matrix and nonlinear calculations. Recomputing after an already rounded LMS value cannot recover lost distinctions. Finite decimal coefficients promoted to Decimal retain their coefficient error; coefficient provenance, precision, operation order and independent references must be frozen. Higher precision reduces errors but does not itself certify mathematical zero or transcendental bounds.

An arbitrary-precision kernel also changes a subtle agreed detail: current authored rounding is over the shortest round-tripping text of a **finite binary result**. Rounding an arbitrary-precision result directly, or converting it to Number first, are different contracts. The former needs an explicit policy amendment; the latter keeps binary quantization at the boundary and cannot promise arbitrary-precision authored output. Exact 18-digit byte adaptation is independent and unchanged. No arbitrary-precision math package, certified-interval approach or performance limit has been evaluated/selected here.

## Confirmed future mixing and gradients

Both libraries offer substantial reusable calculation capability. These APIs supply interpolated colors and samples; they do not by themselves implement DTW's canonical gradient token, reference/expression semantics, stop ownership, target diagnostics or CSS linear/radial/conic geometry and layout. Those remain DTW model/adapter responsibilities, separate from the chosen numerical backend.

| Capability | Color.js 0.7.1 | Culori 4.0.2 |
| --- | --- | --- |
| Mixing / interpolation space | `mix` samples a two-color `range`; explicit interpolation and output spaces, progression and extrapolation. Default space is Lab. | `interpolate` samples multiple colors in an explicit mode, default sRGB; a two-color call yields a weighted mix. Channel overrides and other interpolators are available. |
| Gradient stop calculations | `range` and `steps` provide continuous/discrete samples; optional delta-E step refinement. Positioned multi-stop segmentation would require DTW composition around these two-endpoint APIs. | Positioned multi-stop arrays, omitted-position normalization, interpolation hints and easing are directly supported; `samples` can provide sample positions. Parameter is clamped to `[0,1]` in the pinned interpolation implementation. |
| Hue / alpha / missing conventions | Hue shorter/longer/increasing/decreasing/raw; shorter default. Missing endpoint coordinates carry the other endpoint's value. Optional `premultiplied` excludes hue and preserves missing components; it is not enabled merely by calling `mix`. | Polar mode definitions use shorter hue fixup by default, with longer/increasing/decreasing helpers. Separate `interpolateWithPremultipliedAlpha` API; default interpolation is not that API. Linear piecewise interpolation carries a defined endpoint across a missing partner and leaves two missing endpoints missing. |

Sources checked 8 November: [Color.js interpolation guidance](https://colorjs.io/docs/interpolation), pinned [interpolation implementation](https://github.com/color-js/color.js/blob/v0.7.1/src/interpolation.js) and [missing-value arithmetic](https://github.com/color-js/color.js/blob/v0.7.1/src/util.js); [Culori interpolation API](https://culorijs.org/api/#interpolate), pinned [interpolation](https://github.com/Evercoder/culori/blob/v4.0.2/src/interpolate/interpolate.js), [piecewise missing behavior](https://github.com/Evercoder/culori/blob/v4.0.2/src/interpolate/piecewise.js), [polar defaults](https://github.com/Evercoder/culori/blob/v4.0.2/src/lch/definition.js) and [hue fixups](https://github.com/Evercoder/culori/blob/v4.0.2/src/fixup/hue.js). These are source/API capabilities, not measured future-operation correctness or blanket CSS-gradient conformance.

**Consequential difference:** pinned Color.js `range` converts both endpoints and unconditionally calls `toGamut` on each before interpolation; no no-mapping option is exposed in that inspected path. This does not mean every endpoint changes: already-in-gamut values may remain unchanged, and Lab/OKLAB do not impose RGB's fixed gamut. The risk concerns out-of-gamut endpoints in bounded interpolation spaces. Culori's inspected interpolation implementation converts stops through its converter and has no corresponding gamut-mapping call in that path. This makes Culori structurally promising for explicitly unmapped future mixing; it still inherits its conversion, missing and precision behavior. [Color.js actual path](https://github.com/color-js/color.js/blob/v0.7.1/src/interpolation.js#L173-L178), [Culori actual path](https://github.com/Evercoder/culori/blob/v4.0.2/src/interpolate/interpolate.js).

A hybrid strict kernel plus upstream mixing is therefore not automatically consistent: the library can reconvert endpoints internally, neutralize tiny chroma, carry missing components, map gamut, choose hue arcs or premultiply differently from DTW's strict route. Preconverting stops does not disable Color.js's mapping call. Feeding Culori already-converted same-mode stops can avoid cross-space endpoint conversion, but output conversion, alpha/hue handling, parameter limits and rounded-stop versus raw-stop differences still require a contract and seam fixtures. Custom spaces/modes may unify routes at the cost of maintaining those overrides. Alternatively reuse lower-level interpolation math after owned conversion; that saves some arithmetic while shifting more policy ownership to DTW.

The future operation contract must choose spaces, hue paths, alpha/zero-alpha behavior, missing/powerless rules, extrapolation, duplicate/hard-stop positions, sample/rounding stages and gamut policy. Existing conversion-only alpha-copy rules do not forbid premultiplication inside a separately specified future mix. Conversely confirmed future needs do not authorize silently applying library defaults or extending Increment 003 criteria. Assess those choices before making future API commitments.

## Ownership and maintenance costs

All choices require the same owned policy layer: canonical strings/units, exact byte arithmetic and formatter, missing/neutral eligibility, exact alpha/identity, target constructor, calculation budgets, preview bounds, failures and session atomicity. Owning that boundary does **not** require owning the conversion equations. All choices also require independent expected fixtures and cross-runtime testing: outsourcing math does not outsource our stronger acceptance contract.

| Option | Initial/integration cost | Ongoing burden and principal trade-off |
| --- | --- | --- |
| Color.js + small adapter + raw polar override | Lowest additional empirical uncertainty: existing five-space samples and installed dependency. Adapter avoids parser/serializer defaults; polar override and observability remain work. | Maintain a small divergence plus pinned-version fixture checks. Upstream owns most science/bug fixes if usable paths remain; upgrade changes in matrices/defaults/routes can change accepted candidates. Not currently proven sufficient. |
| Culori + small adapter | Similar policy adapter; normalized HSL mapping, missing handling and independent fixture validation. Raw polar behavior avoids one workaround. | Potentially less polar divergence, but no measured DTW accuracy/guard evidence yet. Generic sRGB routes and built-in neutral equality need audit. Switching libraries is not a precision upgrade. |
| Unified upstream conversion + manipulation backend, with policy adapter | Qualify conversion now and future mixing/gradient rules before adoption. Culori offers positioned stops; Color.js supplies mixing/ranges/steps but its endpoint mapping needs explicit disposition/alternative path. | Best potential to share conversions and benefit from upstream standards/tests across the confirmed roadmap. DTW still owns policy, canonical gradient/expression modeling and acceptance fixtures. Advantage shrinks if custom modes/forks replace most behavior. |
| Either library + owned hotspots / AP fallback | Higher: two numerical paths, eligibility/dispatch/refusal rules, constants and seam fixtures. Useful only for identified reusable library paths and isolated failures. | Maintain upstream integration **and** owned math/fallback. Can be economical when overrides stay narrow; becomes worse than a narrow owned module if most routes are replaced. AP adds a dependency/algorithm qualification cost. |
| Narrow owned five-space module, optional AP math | More initial numerical work: transfers, matrices, HSL, rectangular/polar equations, explicit stages, coefficient provenance, references and runtime verification. Reuse existing Decimal model and constructor. | Full responsibility for numerical bugs, standards corrections, branch/boundary behavior and maintainers who understand it. | Narrow strict owned kernel + upstream manipulation | Add the strict route plus future library integration and explicit consistency/seam tests; reuse upstream interpolation/stops where compatible. | Retains upstream breadth while paying for two route contracts, upgrade coupling and potentially different accepted domains/results. Valuable fallback if strict guards need ownership; not automatically simpler than a unified backend. |
| Full owned manipulation module/library | Highest initial scope: beyond conversion, own mix weights, hue arcs, premultiplied alpha/zero alpha, missing components, positioned/hard stops, interpolation and sampling; add only other operations actually required. | Confirmed future need makes these costs relevant, but DTW takes standards tracking, independent-reference testing, expert review, runtime behavior and public API maintenance. ## Decision boundary and smallest next evidence

| Class | Current conclusion |
| --- | --- |
| Hard incompatibility in a stock path | Color.js default near-neutral OKLCH suppression conflicts with agreed tiny-nonzero behavior; replace/bypass that path. Neither stock library delivers our exact byte policy or all-intermediate refusal contract. This blocks drop-in use, not the entire library. |
| Routine owned adapter work | Exact source/identity/alpha, units, missing eligibility, explicit neutral branches, decimal formatting, constructor validation, serialization/gamut separation and failure/session retention. Required under every alternative. |
| Genuine choice requiring disposition/evidence | Exact observable-stage and uncertainty-refusal specification; how much numerical code reuse survives it; whether AP hotspots justify their complexity and a rounding-basis amendment. Existing guard interpretation and cbrt-refusal proposals cannot silently become requirements. |
| Evidence gap | Culori fixture accuracy, extended/near-neutral behavior, browser equivalence, actual import/bundle effects; full five-space guarded routes and reference ownership for any option. No option closes the gate today. |

Before selection, first resolve the existing narrow guard/refusal clarification with its measured acceptance trade-off. Then authorize only the smallest discriminating evidence: a pinned Culori run of the existing independent fixture set, plus an actual-route inventory showing which required internal coordinates/cancellation signals can be enforced through low-level library reuse and which equations must be owned. Include long-text→Number collision, tiny red, exact/near gray, cbrt-pair collapse, magnitude endpoints, extended P3/HSL, constructor boundaries and explicit unresolved/refusal statuses. Compare ordinary accuracy and guard coverage separately. Add a small future-fit seam assessment using explicit provisional policies: transparent/chromatic endpoints, hue wrap/missing hue, extended colors and positioned stops; demonstrate internal conversions/mapping rather than claiming the strict kernel governs them. It must label policy alternatives, not settle future semantics. This is proposed further research, **not authorization to execute it now**.

If reusable paths remain substantial and guard-compliant, prefer the upstream backend with the simpler verified conversion **and future manipulation** adapter; current source evidence favors testing Culori first, while Color.js retains existing measured conversion evidence. If almost every strict transform must be rewritten, evaluate the narrow-owned/upstream-manipulation hybrid against the cost of coherent custom modes before selecting. Reserve full manipulation ownership for demonstrated pervasive incompatibility or an explicit product choice to fund the expertise/testing burden. Add AP only for a concrete required failure that bounded refusal/ordinary routes cannot address. This weighs the confirmed roadmap without starting its implementation.
