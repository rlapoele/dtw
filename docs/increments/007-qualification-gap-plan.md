### G-02 — finite Safari supervisor probe

Propose a **12-second finite** CPU block in the own worker, with lock acquisition
and a positive “block started” signal. Keep the ordinary stress runner's execute/async
waiting on that worker result; do not return from that command before intervention.
A separate controller process sends the runner's actual exact-own-window close
operation **2 seconds after the start signal**, with a **3-second response deadline**.
These are proposed probe controls, not product limits. Capture independent timestamps;
require actual cessation/lock reacquisition before the natural 12-second completion,
not merely successful HTTP submission. A second own context witnesses lock acquisition.
Run the finite nonintervention control, then three successful controlled repetitions
before claiming reproducibility; preserve all failures. This is a bounded control
probe, not defensive-size data or an unbounded infinite loop.

If close queues behind execute/async, times out, or affects the wrong context, stop:
no new Safari defensive stress. Let only the finite probe finish; do not repeatedly
close, kill Safari.app, terminate all user windows or escalate to a larger fixture.
A WebDriver script timeout is not itself proof the worker stopped. WebDriver defines
command processing and Close Window, but does not establish safaridriver preemption
in this actual pending state. [WebDriver](https://www.w3.org/TR/webdriver2/)

Fallback choices for review: qualify a separate external control path that can stop
only the owned worker/window under that **same** pending state, or use a genuinely
disposable isolated OS/browser environment with an independently proven own-process
supervisor and separate user authorization. A renderer-timer-only worker stop cannot
qualify supervision of blocked renderer work. User-assisted normal steps may support
native observations, but are not a proven automatic 30-second stress watchdog.
If no safe route exists, retain the gap and return an explicit gate decision;
neither dropping Safari nor calling prior maximum observations safely qualified follows.

### G-04 — transaction interleavings, not long sleeps

Hold a bounded native readonly cursor scan with cursor/request barriers; signal that
it is active, issue a write from another own worker, then release the scan through
requests serviced within the native transaction. Reverse order with an active writer
and a waiting scan. Never await an external worker message inside a live acceptance
transaction or simulate ordering with elapsed time. Restrict request keepalive to a
labelled harness barrier with a fixed request ceiling; it is not a product technique.
Test empty/typical first, then the admitted 25×8 MiB scan only after the supervisor gate.
Report writer wait separately from dispatch→complete and scan latency; the stress
catalogue has no 2-second typical-workload deadline. Any starvation/watchdog expiry
is failed/inconclusive and requires review of the same-record transaction strategy,
not silently splitting catalogue authority or weakening strict acknowledgement.

For capacity, seed 24 records, prepare two different-project insertions in separate
workers, issue both before releasing the first acceptance barrier; exactly one can
fill slot 25. Repeat with one unavailable/unsupported seeded record included in count.
For replacement, prepare protection for revision A, issue a competing accepted B
before replacement checks, then replacement must conflict; reverse order verifies
normal complete replacement followed by the expected stale contender conflict.
A controlled uncooperative native writer may bypass Web Locks solely as a labelled
CAS test; ordinary cooperating owners must never both become writable. Repeat each
material interleaving three times/engine, reversed winners; retain exact before/after,
latest-command metadata and current incarnation. No exhaustive scheduling claim.
[IDB transaction scheduling](https://www.w3.org/TR/IndexedDB/#transaction-scheduling)
