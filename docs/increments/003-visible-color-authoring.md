Let a design-system author create a project, organize a small color vocabulary, author a primitive and semantic alias, revise their values, and understand the resulting relationship through a desktop-oriented browser interface.

The proposed value is immediate interaction feedback: can an author distinguish an authored alias from its resolved color, deliberately change the dependency, and understand a rejected cycle without reading tests or calling APIs? It is a **session-only authoring prototype**, with a reusable renderer, rather than a durable workbench. It is suitable for trying the workflow with disposable examples, not retaining real project work.

## Scope

- Included: a local browser entry point using the existing single-package Vite scaffold; one active project per page lifetime; named root/nested groups; root/group color token placement; group rename; literal/whole-value alias creation and explicit value revision; a token list, contextual editor and authored/resolved inspector. Reuse the existing application operations and in-memory adapter, with one sequential writer.
- Creation exposes name, parent and optional primitive/semantic layer, and explicitly discloses the initial opaque sRGB `[0, 0, 0]`, alpha `1`, before Create as specified in the written supplement. Type is explicitly shown as color. Under agreed D3, the delivery surface explicitly passes `regeneration: "allowed"` for new manual creations; no regeneration control is required. This agreed delivery default changes neither domain semantics nor Increment 001's explicit application input. Optional descriptions and semantic roles need not be editable in this prototype; omitted metadata is not inferred from names, layers or alias form. Existing metadata remains visible in inspection and unchanged by value revision.
- Use the accepted neutral Precision direction for hierarchy, density, separators and contextual inspection. The illustrative mockup does not require its exact controls, variations, ramps, scales, graph layout, export menu or saved indicator. A modest list and textual dependency trace are sufficient; no decorative unsupported features.
- Exact-field editing supports all five existing color spaces, three canonical Decimal-or-`none` component strings and explicit alpha, without binary-number readback of direct input. Under the [5 November agreed color policy](003-color-policy-proposal.md), sRGB 0–255 entry uses exact decimal division, retaining terminating quotients and otherwise rounding to 18 significant digits, ties to even. Changing the displayed space derives a temporary representation from the one authoritative literal draft and does not dirty it. A deliberate component edit in another view promotes that representation to the draft, with calculated channels rounded to 12 significant digits, ties to even, and the edited channel entered exactly. Alpha-only edits retain the authoritative space and exact alpha. Apply alone commits the authoritative draft, even while another representation is displayed; successful Apply resets the view to that authored space. Entry-scale inspection and same-space requests preserve exact values. Missing/powerless components, calculated limits, final constructor validation and failure retention follow that policy. Native one-dimensional component/alpha sliders supplement exact entry under the identified design below. No localized parser, HEX editing, two-dimensional picker, gamut mapping or fallback generation is introduced.
- Preview renders direct numeric in-range sRGB using exact bounds, or an eligible approximate conversion from another supported space, outside the domain. The agreed initial cross-space display-only boundary allowance is `1e-10`, subject to numerical validation; no authored clipping or gamut mapping is permitted. Missing components except the policy's exactly powerless-hue cases, out-of-gamut results and calculation failures receive an explanation rather than a substituted fallback. Authored values remain fully inspectable/editable even without a specimen. Browser rendering is illustrative, not an exact color-management or target-compatibility promise.
- Excluded: durable save/open, browser storage, backup/restore, snapshot download presented as backup, token import/export, compatibility profiles, manifest/service worker/install/offline acceptance, Electron packaging/bridge, project listing/switching, multiple tabs sharing data, variation authoring, other value types, component tokens, incomplete-token creation, moves/deletion, undo/history, automatic repair and naming-policy changes. Test-only fixtures may demonstrate existing unsupported/broken states without becoming a loader API.

## Acceptance criteria

AC-1–AC-8 are the agreed criteria, not completed acceptance. They incorporate the agreed numerical bundle, adopted stack and creation default, and the identified V6 interaction design. No wording authorizes implementation or claims numerical validation.

- AC-1: From an empty browser page, an author creates a project, root and nested namespace groups, and a literal color token at the root or in a group; the project may remain empty. The host supplies opaque identities to application calls; names are preserved exactly, including empty project names. An `(unnamed project)` label is presentation only, never a replacement stored name. The disclosed initial literal is deliberately created before opening revision; failed creation retains inputs without a write. Group rename refreshes derived paths without changing identities or alias targets. Selection and target controls use stable IDs and visibly disambiguate duplicate/empty names and duplicate derived paths; structural validation is not labeled name uniqueness.
- AC-2: The author creates a semantic-layer alias to an existing same-project color token, sees its authored target separately from its resolved color and ordered domain trace, revises the primitive and sees dependent inspection refresh to the new value. New manual creations explicitly receive `regeneration: "allowed"` under agreed D3. Retargeting and literal↔reference replacement require explicit submission; switching form mode or inspecting a token never overwrites its stored value or silently copies a resolved literal. Value revision preserves all other token data and regeneration policy, including a protected color test fixture, which remains manually editable with protection visibly retained. Existing descriptions, semantic roles and other metadata remain available read-only. Eligible targets include valid same-project color alias chains; no primitive-only or layer-direction restriction is introduced.
- AC-3: After the disclosed initial creation, exact text fields revise literals in each supported space, preserve long canonical Decimal strings, `none`, alpha and extended RGB coordinates, and expose the constructor's hue normalization after successful submission. Noncanonical Decimal or invalid range input fails without a write and leaves the draft correctable. sRGB entry-scale toggles and identity conversions preserve exact coordinates and do not dirty the draft; actual byte edits change only edited channels under the agreed decimal policy. View-only space exploration derives every alternate representation directly from the authoritative draft; returning through any unedited sequence restores its exact text without drift or dirtying. Actual component edits in another space promote that representation under the [color policy](003-color-policy-proposal.md); alpha-only edits retain the authoritative space. Apply commits the authoritative draft, not a merely displayed representation. Native sliders deliberately edit within their specified visual intervals/steps; `none`, invalid and outside-interval values keep exact entry and an explanation without a clipped or fabricated thumb. Tracks are illustrative, not predictive or canonical bounds. Verify its rounding, exact-neutral/tiny-nonzero handling, bounded calculation, final constructor validation and retained source/draft on failure. Preview follows the bounded scope above; display-only conversion/rounding and unavailable specimens never rewrite authored data, flatten aliases or choose a fallback. Numerical/library gates must have evidence before acceptance; unresolved gates are not passing criteria.
- AC-4: Self/indirect cycles and invalid targets rejected by whole-candidate namespace/reference checks appear as understandable operation failures; prior authored data and resolved inspection remain unchanged. Namespace diagnostics, reference diagnostics and resolution outcomes remain distinguishable, with existing codes/details available. A broken-data fixture demonstrates unresolved inspection and the existing one-edit repair limit: unrelated diagnostics still block repair. No success message claims complete validity or target compatibility.
- AC-5: Draft fields remain separate from stored authored data until explicit submission. Literal and Reference drafts independently retain their fields, reference target, view, scale and valid/raw incomplete byte text across mode switching and pane collapse. An applied alias begins a new literal form blank; it is never initialized from its resolved value. Cancel leaves stored data unchanged and discards both drafts, restoring the applied baseline. Successful Apply commits only the active form, establishes its new baseline and clears the inactive draft; rejected Apply retains both. Departure protects hidden edits as well as active ones. Application failures retain the draft and identify the failing operation; success is displayed only after the operation succeeds. Controlled load/commit-failure fixtures demonstrate unchanged data and distinguish storage failure from invalid authoring. A failed read arriving during an open form retains inputs and last successful data, disables project mutation and exposes Retry; only a successful read restores eligibility. Creation/rename failures likewise retain the form and identify the failed operation. Error focus, correction and return behavior remain meaningful when the initiating control is unavailable. Unsupported/ineligible fixture tokens remain inspectable and cannot enter the color-revision flow by silently losing data.
- AC-6: The interface persistently states that work exists only in this page's memory and will be lost on reload, closing or navigation; it never says saved locally. Reload demonstrably opens an empty session with no recovery/backup claim. Application state is not written to browser persistence or a server. Creating the project establishes its identity before authoring; a browser-generated opaque UUID is supplied at the delivery boundary under agreed D3, without changing domain constructors or selecting a future file identity scheme.
- AC-7: The entire create→alias→revise→inspect flow is keyboard-operable with native semantic controls, associated labels, visible focus, sensible focus after submissions/cancellation, and programmatically connected errors. Success/failure updates are announced; meaning does not depend on color alone. The same workflow remains usable at desktop, tablet and mobile widths, including 320px width and a short-height sample; at 200% actual browser zoom controls and diagnostics remain reachable without overlap or lost actions. Test long exact values/identities/errors, drawer/modals, selected-row context and sticky actions. Resizing/collapse preserves drafts; accepted selection of a different token resets inspector reading to the top, while same-token continuation and rejected departure preserve reading position. Hidden panel contents leave the tab order. Record assistive-technology and virtual-keyboard check coverage and limits; viewport resizing does not establish zoom evidence. Exact controls follow the task, not the reference board's full feature set.
- AC-8: A production build and real-browser run exercise these criteria through the shared application operations. The UI does not reconstruct namespace/reference/resolution semantics. Domain/application host independence and all existing tests remain intact; new browser/framework types are isolated from their host-independent checks. No new canonical persistence representation, concurrency protocol, interchange adapter, general state-management framework, backend, or package split is introduced.

## Guard and cancellation evidence and proposed clarification

The [evidence report](003-guards-cancellation-report.md), [independent review](003-guards-cancellation-review.md) and frozen scratch manifest identify the completed bounded investigation. Twenty-four targeted cases demonstrate useful ordinary acceptance, internal magnitude violations (including exact-neutral transfer), exact linear zero/nonzero discrimination and a near-gray cube-root distinction loss missed by source/endpoint checks. Coordinate-stage and scalar-term guard readings differ on the measured tiny-red `1e-97` case. Both review findings were corrected and rechecked; reproductions match. This does not close the full numerical gate or select a dependency.

**Recommendation, not an adopted amendment:** prefer a small explicitly owned observable equation route for authored conversion over an opaque `.to()` wrapper. Proposed clarification for user review:

1. Apply the unchanged magnitude limits to a versioned inventory of named coordinate stages actually used: source, linear RGB (including exact-neutral linearization), XYZ, LMS, cube-root LMS, rectangular/polar coordinates and final candidates. Individual products/partial sums and native Math internals would not receive these magnitude limits. This is a proposed definition, not a silent narrowing of the current “intermediate results” wording; the alternative scalar reading measurably refuses additional inputs.
2. Permit a narrowly specified conservative numerical refusal where lost distinctions make required chroma/hue unreliable, preserving exact source editing and identity. Do not adopt every injective-function collision as automatically required refusal or copy the scratch `1e-12` diagnostic as policy. Define the affected condition, failure meaning and acceptance/refusal fixtures explicitly; no arbitrary near-neutral epsilon or universal mathematical certification is proposed.

After user disposition, prepare a short route-and-refusal specification identifying stages, failure categories and required regression fixtures before any eventual kernel implementation. This specification and production implementation are not started or authorized by the completed research. Missing routes, broader cancellation coverage, browser/runtime checks and application integration remain gates. ### Findings and required decisions

#### 1. Before agreement: reconcile D2/AC-3 with requested conversion and preview UX

**Concrete mismatch:** the Scope and agreed D2 exclude conversion, clear channels on space change and preview only numeric in-range sRGB. V4 instead offers byte-scale edits, converts the current draft when changing space, and previews other spaces through approximate sRGB conversion (`LiteralFields.tsx:9–17`; `color-tools.ts:8–74`; proposal README:104–133). The user's requested exploration and approval for review do not select its numerical policies.

**Recommendation — proposed:** retain the user-requested V4 interaction direction and prepare a bounded conversion/preview specification with representative numerical fixtures before final agreement or implementation. The user should review an explicit proposal, not have to invent tolerances. It must distinguish unchanged exact text from newly calculated candidate values, specify byte division/formatting and conversion precision, repeated conversions, missing/powerless hue, alpha, unsupported magnitudes, invalid/out-of-range results, preview gamut tests and failure behavior. Keep preview approximation separate from authored conversion and target compatibility. Direct exact editing, extended RGB, `none`, explicit Apply and no implicit alias flattening remain constraints.

The prototype's candidate policies are **12 fractional places for calculated components, six for derived byte display, cross-space preview boundary tolerance `1e-10`, no gamut mapping, restricted missing-hue conversion, and Color.js `0.7.1`**. They are evidence to evaluate, not adopted defaults. For example, `1 / 255` is non-terminating in Decimal; choosing its rounding changes authored candidate values. Fixtures should include all space pairs, long/tiny exact inputs, extended RGB and boundary colors, achromatic numeric/missing hue, other missing components, incomplete text, alpha and conversion rejection. The existing eight helper tests sample some of these; they do not establish an acceptable production policy or exhaustive numerical correctness.

**Boundary already established:** deterministic authored conversion/manipulation belongs in the domain engine, coordinated through application operations; browser specimens belong outside it ([architecture](../project/architecture.md#domain-engine), lines 105–131; [color model](../design-tokens/conceptual-model.md#color-literals), lines 983–1031). A presentation-only Color.js helper must not become the sole implementation of authored conversion. The proposal must identify the narrow reusable operation boundary and verification needed; no package split or generic color framework is implied. A preview-only conversion may remain an outer rendering concern and cannot write authored data.

**Alternative:** explicitly retain original exact-only D2 and remove byte/conversion/cross-space-preview controls from the application design. This keeps 003 smaller but loses requested V4 behavior and would be a material revision requiring user review. No such rollback is recommended or selected here. If the V4 direction is retained, amend Scope, D2, AC-3 and verification together only after agreement, and record the bounded choices in the owning color/open-question documents without relaxing the exact canonical model.

Verify current compatibility, official integration instructions, exact package versions and lockfile effects during the authorized technical preparation. Color.js remains a separate finding-1 decision. No router, general state library, backend, persistence or package split is needed by this slice.

These are material missing workflow states; present the supplement to the user before renewed analyst review.
