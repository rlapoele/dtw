## Outcome

Let a design-system author create a project, organize a small color vocabulary, author a primitive and semantic alias, revise their values, and understand the resulting relationship through a desktop-oriented browser interface.

The proposed value is immediate interaction feedback: can an author distinguish an authored alias from its resolved color, deliberately change the dependency, and understand a rejected cycle without reading tests or calling APIs? It is a **session-only authoring prototype**, with a reusable renderer, rather than a durable workbench. It is suitable for trying the workflow with disposable examples, not retaining real project work.

### Comparison and recommendation

| Consideration | Durable retention plus independent backup/restore | First visible authoring slice |
|---|---|---|
| User value | Keep and recover authored work beyond a process/browser lifetime and outside one origin. Most useful when there is an authoring surface to use it. | Try the existing create→alias→revise→inspect loop directly; assess interaction, clarity and accessibility now. Work is lost at session end. |
| Minimum honest scope | Versioned authored-project representation with explicit coverage; durable save/open; independent user-held backup and transactional restore; diagnostics and failure evidence. Merely serializing the current snapshot is insufficient. | One active project, grouping, unconditional color/alias creation and revision, exact authored/resolved inspection, visible diagnostics, and explicit retention limits. No complete PWA claim. |
| Decisions required | Schema/manifest versus DTCG; coverage of axes/presets and implemented values/metadata; versions/migrations/unknown data; identity/conflicts and repairable data; browser or filesystem host, store and file access; asynchronous application boundary if the adapter needs it. | Renderer technology; exact-field editing and bounded preview; session identity/lifecycle; observable authoring/accessibility scope and acceptance of session-only staging. |
| Main risks | Locking a premature schema; dropping supported data; falsely treating operational snapshots or interchange as complete backup; interrupted writes and corrupt restores. | Authors mistake a prototype for safe storage; structured editing is less approachable than a picker; UI state diverges from application truth; storage and asynchronous delivery assumptions remain untested. |
| Verification | Exact round trips for declared coverage, independent backup after clearing the primary store, reopened-host recovery, malformed/unsupported input rejection, preserved repairable references, identity conflicts and failed-write/restore atomicity. | Real-browser authoring and rejection scenarios, keyboard/accessibility checks, dependent refresh, exact inputs, ID-based duplicate-name handling, refresh-loss demonstration and production build. |
| PWA/Electron progress | Establishes the ownership/recovery prerequisite for the complete PWA and a replaceable storage boundary useful to Electron. Does not validate the visible authoring experience or complete the PWA alone. | Establishes the renderer and interaction evidence reusable by Electron. Still needs retention/backup, explicit interchange and install/offline behavior before the complete PWA, then immediately the Electron milestone. |

**Recommendation — proposed:** choose visible authoring for 003. Two completed operation-only increments now support a real create/edit/dependency loop; direct author feedback is the next distinct uncertainty to test. This recommendation prioritizes product learning, not the avoidance of persistence decisions. Agreeing it deliberately stages a session-only prototype ahead of retention; it does not relax the established requirement for independent backup/restore in the first complete browser experience.

**Conditional alternative:** if the next outcome must be keeping real authored work, choose retention/backup instead and revise this draft before implementation. That contract must explicitly select its host and asynchronous/synchronous boundary, version and coverage, and restore semantics. It must cover the implemented authored model, including project/group/token metadata, incomplete tokens, conditions, axes, presets, literal/reference/expression/composite values and exact decimals, or name a bounded representation and refuse unsupported project data without silently dropping it. The current `ProjectSnapshot` lacks axes/presets and is not a complete project schema. A proposed versioned JSON envelope would be a canonical persistence choice requiring agreement, not DTCG interchange. Restore should distinguish malformed structures from recognizable repairable authored references; preserve identities and diagnostics; reject unsupported versions/fields or preserve them through an agreed mechanism; and never overwrite a conflicting project or partly commit a failed restore. These choices are not made by this alternative's description.

## Scope

- Included: a local browser entry point using the existing single-package Vite scaffold; one active project per page lifetime; named root/nested groups; root/group color token placement; group rename; literal/whole-value alias creation and explicit value revision; a token list, contextual editor and authored/resolved inspector. Reuse the existing application operations and in-memory adapter, with one sequential writer.
- Creation exposes name, parent and optional primitive/semantic layer. Type is explicitly shown as color. Under proposed D3, the delivery surface explicitly passes `regeneration: "allowed"` for new manual creations; no regeneration control is required. This proposed delivery default changes neither domain semantics nor Increment 001's explicit application input. Optional descriptions and semantic roles need not be editable in this prototype; omitted metadata is not inferred from names, layers or alias form. Existing metadata remains visible in inspection and unchanged by value revision.
- Use the accepted neutral Precision direction for hierarchy, density, separators and contextual inspection. The illustrative mockup does not require its exact controls, variations, ramps, scales, graph layout, export menu or saved indicator. A modest list and textual dependency trace are sufficient; no decorative unsupported features.
- Exact-field editing supports all five existing color spaces, three canonical Decimal-or-`none` component strings and explicit alpha. No binary-number round trip, localized/display notation parser, color conversion, HEX editing, picker, gamut mapping or fallback policy is introduced. Changing the space is an explicit new-value draft, with component fields cleared for re-entry, not an automatic conversion.
- Preview is limited to numeric sRGB values within nominal component ranges, with alpha, rendered outside the domain. Other spaces, missing components and extended coordinates remain fully inspectable/editable as exact text with a preview-unavailable explanation. Browser rendering is illustrative, not an exact color-management or target-compatibility promise.
- Excluded: durable save/open, browser storage, backup/restore, snapshot download presented as backup, token import/export, compatibility profiles, manifest/service worker/install/offline acceptance, Electron packaging/bridge, project listing/switching, multiple tabs sharing data, variation authoring, other value types, component tokens, incomplete-token creation, moves/deletion, undo/history, automatic repair and naming-policy changes. Test-only fixtures may demonstrate existing unsupported/broken states without becoming a loader API.

## Acceptance criteria

AC-1–AC-8 are proposed and not agreed.

- AC-1: From an empty browser page, an author creates a project, root and nested namespace groups, and a literal color token at the root or in a group; the project may remain empty. The host supplies opaque identities to application calls; names are preserved exactly. Group rename refreshes derived paths without changing identities or alias targets. Selection and target controls use stable IDs and visibly disambiguate duplicate/empty names and duplicate derived paths; structural validation is not labeled name uniqueness.
- AC-2: The author creates a semantic-layer alias to an existing same-project color token, sees its authored target separately from its resolved color and ordered domain trace, revises the primitive and sees dependent inspection refresh to the new value. New manual creations explicitly receive `regeneration: "allowed"` under proposed D3. Retargeting and literal↔reference replacement require explicit submission; switching form mode or inspecting a token never overwrites its stored value or silently copies a resolved literal. Value revision preserves all other token data and regeneration policy, including a protected test fixture, which remains manually editable.
- AC-3: Exact text fields create/revise literals in each supported space, preserve long canonical Decimal strings, `none`, alpha and extended RGB coordinates, and expose the constructor's current hue normalization after a successful submission. Noncanonical Decimal or invalid range input fails without a write and leaves the draft available to correct. Preview follows the bounded scope above; changing or failing to render it never changes authored values or chooses a fallback.
- AC-4: Self/indirect cycles and invalid targets rejected by whole-candidate namespace/reference checks appear as understandable operation failures; prior authored data and resolved inspection remain unchanged. Namespace diagnostics, reference diagnostics and resolution outcomes remain distinguishable, with existing codes/details available. A broken-data fixture demonstrates unresolved inspection and the existing one-edit repair limit: unrelated diagnostics still block repair. No success message claims complete validity or target compatibility.
- AC-5: Draft fields remain separate from stored authored data until explicit submission. Cancel leaves stored data unchanged. Application failures retain the draft and identify the failing operation; success is displayed only after the operation succeeds. Controlled load/commit-failure fixtures demonstrate unchanged data and distinguish storage failure from invalid authoring. Unsupported/ineligible fixture tokens remain inspectable and cannot enter the color-revision flow by silently losing data.
- AC-6: The interface persistently states that work exists only in this page's memory and will be lost on reload, closing or navigation; it never says saved locally. Reload demonstrably opens an empty session with no recovery/backup claim. Application state is not written to browser persistence or a server. Creating the project establishes its identity before authoring; a browser-generated opaque UUID is proposed at the delivery boundary, without changing domain constructors or selecting a future file identity scheme.
- AC-7: The entire create→alias→revise→inspect flow is keyboard-operable with native semantic controls, associated labels, visible focus, sensible focus after submissions/cancellation, and programmatically connected errors. Success/failure updates are announced; meaning does not depend on color alone. At desktop widths the project/list/editor/inspection hierarchy remains usable; at 200% zoom controls and diagnostics remain reachable without overlap or lost actions. Exact controls follow the task, not the reference board's full feature set.
- AC-8: A production build and real-browser run exercise these criteria through the shared application operations. The UI does not reconstruct namespace/reference/resolution semantics. Domain/application host independence and all existing tests remain intact; new browser/framework types are isolated from their host-independent checks. No new canonical persistence representation, concurrency protocol, interchange adapter, general state-management framework, backend, or package split is introduced.

## Decisions and open questions

### Established constraints and implementation evidence

- [Initial browser scope](../project/product-concept.md#initial-project-experience) requires complete independent project retention/restore as distinct from named-profile token interchange. The complete PWA precedes the immediately following Electron validation. Neither previous increment authorizes a no-UI restriction for 003.
- [Current operations](../../src/application/authoring.ts) already expose the proposed authoring and inspection semantics; [revision tests](../../test/application/color-revision.test.ts), [authoring tests](../../test/application/authoring.test.ts) and [repairable-data tests](../../test/application/repairable-data.test.ts) substantiate their boundaries. Sibling-name enforcement remains deferred; labels are not identities.
- The synchronous [storage port](../../src/application/project-storage.ts) and detached [in-memory adapter](../../src/adapters/in-memory-project-storage.ts) prove sequential coordination. They do not validate durable/browser storage or an asynchronous bridge. The operational snapshot is expressly not a canonical file schema, and does not contain axes or presets.

### Four proposed decision bundles — resolve before implementation

1. **D1 — Priority and retention boundary.** Recommend the visible, session-only slice and its disposable-example usage; alternatively select retention/backup and replace this draft's UI criteria. Agreement must explicitly accept postponing safe real-work retention. Do not combine both just to avoid choosing.
2. **D2 — Authoring and preview.** Recommend the exact structured color/alias workflow, explicit submissions and bounded sRGB specimen above. This tests the existing semantics without choosing conversion/HEX/picker policies. Accept that this is useful to evaluate authoring and relationships, but less approachable than the intended richer visual editor.
3. **D3 — Session and identity.** Recommend one active project per page, one in-memory writer, generated opaque UUIDs supplied by the host, an explicit optional-layer input and existing whole-candidate rejection/repair policy. Propose a delivery default that passes `regeneration: "allowed"` for new manual creations without requiring a regeneration control; existing policies remain visible/preserved, and protection does not block manual revision. This default requires user agreement and does not change domain or Increment 001 semantics. Keep duplicate-name disambiguation in presentation; defer naming equality/collisions, project switching, persistence schema and async port migration.
4. **D4 — Renderer and milestone boundary.** Recommend React with TypeScript, native controls and ordinary CSS in the existing single package, without a router/component suite/global state library. Keep domain/application checks host-independent; any browser/TSX compiler setup must be explicitly scoped to delivery code. Agree that 003 is an incomplete browser prototype; next contract durable retention/backup, then explicit interchange and offline/install acceptance needed to complete the PWA, immediately followed by Electron validation. This proposed follow-on ordering is not implementation authorization.

For D4, **engineering judgment:** native HTML/TypeScript has less dependency/setup cost for this small interface and can also be reused in Electron. React is proportionate if this is the growing workbench renderer: draft forms, selection, diagnostics and dependent readback are already coordinated views; components and declarative updates offer a maintainable basis. It adds runtime dependencies, TSX/build integration and state-discipline requirements; it neither supplies persistence nor guarantees accessibility. Both options preserve the same canonical architecture. Selecting native HTML/TypeScript instead changes delivery implementation and checks, not the workflow or domain criteria.

Primary-source check, **3 November 2026**: [Vite documents both vanilla-ts and react-ts templates](https://vite.dev/guide/#trying-vite-online). React documents [controlled string inputs and update handlers](https://react.dev/reference/react-dom/components/input), and [avoiding duplicated state, including ID-based selection](https://react.dev/learn/choosing-the-state-structure). These support the proposed draft/selection approach; they do not establish that React is necessary. For DTW, retain exact input strings rather than adopting examples that coerce numeric input to `Number`. If React is agreed, verify compatible exact dependency versions, official integration guidance and lockfile effects before implementation; this draft does not assert a package version.

### Deferred

Canonical schema/manifest and versioning, durable adapters and asynchronous application calls, complete backup coverage/restore conflicts, first interchange profile, full PWA acceptance and detailed Electron prototype criteria remain unresolved. Implementation after agreement must record the agreed direction in affected owning documents and the status handoff; this draft alone changes none of them.

## Verification approach

- Preserve domain/application regression suites; test only genuinely new coordination/parsing behavior with focused tests. Cover AC-1–AC-5 through browser interaction backed by the real operations, using isolated failure/repairable fixtures where normal authoring cannot create the state. Check actual application readback, not merely form text, for identity, exact values, rejected writes and metadata preservation.
- Capture browser evidence of the normal workflow, duplicate-path selection, failed cycle, correction/cancellation, bounded/unavailable previews and reload loss (AC-1–AC-6). Test all five spaces, a long decimal, `none`, extended RGB, alpha, hue normalization and invalid canonical input. Inspect console errors and runtime requests; no network service should receive project data.
- Manually verify keyboard flow, focus, labels/error announcements, non-color cues, desktop layout and 200% zoom; record browser/version, viewport and observations rather than claiming formal WCAG conformance (AC-7). Inspect against the accepted reference for visual direction, not pixel equality.
- Run `npm run typecheck`, `npm test`, `npm run build`, `npm run preview` for the real-browser production check, and `git diff --check` (AC-8). Scope delivery types/configuration and dependencies explicitly; document any needed browser-test command once agreed. Map developer and separate reviewer evidence to AC IDs in the eventual completion report.
- No durable-recovery, full-PWA/install/offline, external interchange, concurrency or Electron evidence is claimed. In-memory browser success leaves the asynchronous delivery/storage risk open.
