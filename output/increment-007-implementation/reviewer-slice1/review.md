## Required findings

1. **R1 — Runtime-validate operation inputs and responses at the worker boundary.** `src/presentation/host/workbench.worker.ts:24–30` checks only request ID and operation name, then asserts the input type and invokes the handler. `worker-client.ts:12/19` asserts and trusts the response and operation result. Neither verifies closed per-operation shapes, command discriminants, project/revision correlation or result payloads. The codec validates an eventual snapshot, not these transport messages; read/consume/leave requests do not pass that codec at all. Malformed output can resolve a pending command as an unvalidated success. Add explicit narrow input/result validators for each named operation, retain request/operation correlation and fail closed on invalid responses. This implements the agreed B-2 boundary rather than adding a schema framework.

2. **R2 — Validate the whole retained record before reading its fields, and reject blank internal IDs.** `src/application/retention/record.ts:4–13` accepts nonplain objects/accessors and then reads them; `internalId` accepts whitespace-only revision/command/incarnation strings. F-1/F-2 require plain descriptor-safe retained inputs and nonblank internal IDs. Reviewer probes demonstrate both an accepted whitespace revision/command ID and execution of a revision getter. Validate descriptors/prototypes recursively before field access and use a nonblank check without rewriting accepted strings. Keep authored opaque IDs, including empty/whitespace, permitted.

3. **R3 — Emit the agreed schema-member order.** `src/application/retention/codec.ts:125/168` alphabetically sorts every object's keys. The emitted wrapper starts `authoredVersion, createdAt, format, formatVersion, snapshot`, whereas F-1 explicitly specifies `format, formatVersion, authoredVersion, createdAt, snapshot`, with schema order for authored records. The result is deterministic but differs from the agreed portable format. Use an explicit closed-shape ordered writer and preserve array/string content unchanged; add exact output assertions.

4. **R4 — Make strict-decoder rejection tests discriminate the intended invariant.** `test/application/retention/codec.test.ts:9–10` supplies objects that are not valid backup wrappers, so they reject even if duplicate-key or numeric-lexeme checks are removed. The reviewer copied only codec.ts and changed the duplicate-key guard to false; all ten codec tests remained green. Add otherwise-valid complete wrappers with nested duplicate decoded keys and numeric substitutions in valid numeric fields, plus positive controls. Require the duplicate-guard mutation to fail. The mutation copy/config is local reviewer evidence, not production source.

5. **R5 — Verify readback belongs to the accepted database/revision before marking it available.** `src/application/retention/service.ts:17` only checks that some record exists and its snapshot is admissible. It ignores incarnation, revision and acceptance metadata, then returns the attempted candidate as available. A reviewer port probe changes the database incarnation between commit and readback and still receives `retained/readback: available`. Keep the known acceptance, but report changed/missing/unverifiable accepted state honestly; if a newer legitimate revision exists, identify that explicitly rather than imply the attempted state is current.

6. **R6 — Match the full original receipt when reconciling uncertain acceptance.** `src/application/retention/service.ts:73` matches only commandId. A reviewer probe returns a valid-shape createGroup receipt/result for an uncertain createProject using the same ID; the application declares the original createProject retained. Match operation, result kind and exact result ID as well as command/database identity, and validate their relationship to the stored snapshot where the record contract requires it. Conflicting evidence must remain unknown, without consuming or replaying the original attempt.

7. **R7 — Remove the application-to-concrete-adapter dependency.** `src/application/retention/service.ts:3/55` imports and instantiates `@adapters/in-memory-project-storage`. This is an infrastructure adapter used as a candidate engine inside the application layer, reversing the repository's delivery → application → domain dependency rule. Extract the existing deterministic candidate preparation into application-owned code or a small application-local storage implementation; retain the in-memory adapter as an outer test/delivery adapter. Do not create a generic engine/registry to solve this single boundary.
