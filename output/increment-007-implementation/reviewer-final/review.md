## Required findings

### F1 — Synchronize a clean editor when its applied baseline changes

`src/presentation/features/workbench/components/Editor.tsx:104–115` updates `baselineRevision` when a new revision arrives, but does not update `session` or `initial.current` when that session is clean. Same-project replacement refreshes the inspection without remounting the Editor. Its Currently applied/source data therefore advances while its editable fields still hold the previous applied components. The next single-channel edit submits the stale remaining channels against the new revision; no dirty-baseline comparison is triggered because the editor was clean at refresh.

Independent actual native **Chrome 157.0.8103.50**, disposable own profile, production origin `http://127.0.0.1:4332/`, reproduced this through the real UI: create a zero-valued color, leave the selected editor clean, stage a supported same-ID backup with components `0.8 / 0.6 / 0.4`, download current-local protection, acknowledge, and replace the complete project. The complete applied source then reads `0.8 / 0.6 / 0.4`, while Red/Green/Blue inputs still display `0 / 0 / 0`. There were no page errors. Evidence: `clean-replacement.json`, screenshot and executable probe beside this report. Initial sandboxed launch failed before Chrome connected; the authorized isolated execution produced the counterexample. No user browser or clipboard was accessed.

On a clean baseline change, synchronize the applied literal/reference sessions and baseline consistently, preserving the agreed passive view/scale choices. Continue preserving all dirty raw sessions and requiring deliberate review/reapply when their baseline changed. Add actual clean literal→literal, literal↔reference and unrelated-revision regressions. Verify a subsequent one-channel edit preserves the newly applied untouched components/alpha, not merely the field display.

### F2 — Bound derived paths without applying authored admission caps to display projections

`src/application/retention/projections.ts` eagerly includes every full derived path in context and joins complete paths into row labels. `validateHostOutput` then applies snapshot-budgeted `plainTree(output)` to those derived DTOs. This conflates authored admission with amplified derived presentation and makes small, supported, backuppable projects wholly unavailable.

Two deterministic isolated reviewer probes confirm:

- One root group name of exactly 65,536 units and a child token named `t` passes snapshot and complete-backup admission. Context passes, but the joined row label is 65,540 units and the row response rejects with `decoded-string`.
- Seventy tokens under a group named with 60,000 units produce a complete backup below 80 KB. Repeating the path in context exceeds 4,194,304 transport string units and rejects with `decoded-string-total`.

The actual refresh path catches either transport failure as project-read unavailable and blocks writing, rather than showing a bounded derived-path-unavailable state with exact authored content intact. This violates F-5/AC-21's separation between admitted authored data and unavailable derived work. It also prevents identity-safe inspection of otherwise supported content.

Apply the agreed derived path/work ceilings before expanding/joining large paths, and use bounded display DTO/resource feedback distinct from canonical admission. Avoid repeating full ancestry across the entire context; preserve complete membership/exact identities and the on-demand exact-source route. Do not lower authored limits, truncate authored names or fabricate partial paths. Return any genuinely new paging/navigation interaction for the established design review instead of silently changing scope. Probe source/config is beside this report; both counterexample tests pass.
