# Design Token Workbench

A desktop-first, local-first design-token workbench. Product and domain discovery documents live in `docs/`; the latest handoff is in [docs/status/current.md](docs/status/current.md).

The accepted [visual direction and reference image](docs/project/visual-direction.md) guide subsequent interface design and prototyping.

## Development workflow

Substantial increments use separate analyst, developer, and reviewer agents with an agreed contract and acceptance evidence. A designer joins for substantial interaction or interface decisions: the user reviews and requests changes to design proposals before analyst review, then agrees the resulting contract and design before authorizing implementation. See the [workflow and role instructions](docs/workflow/agent-roles.md), [increment templates](docs/increments/README.md), and [Increment 001 contract](docs/increments/001-in-memory-authoring-workflow.md).

## Browser authoring and domain core

The scaffold uses TypeScript, Vite, Vitest, and npm. The browser renderer uses React, Base UI, Tailwind and Heroicons; pure bounded color calculations use Culori. `package-lock.json` records exact resolved versions. The host-independent domain code implements exact canonical Decimal validation and comparison; boolean, number, dimension, percentage, duration, font family, font weight, color, and cubic Bézier literal construction; variation axes, conditions, selection completion, assignment matching, and theme presets; the core `Project` entity and initial `Token` aggregate lifecycle; namespace groups, structural validation, and path derivation; stable-ID token references with project-scoped validation; and literal, alias, and portable number/dimension expression resolution. Token assignments accept the implemented literal subset, references, portable expressions, and the transition, typography, and shadow composites. Shared application operations now provide a narrow in-memory color-authoring workflow; the browser now exposes those operations through a session-only color-authoring interface. There is no durable storage.

The scaffold was verified using Node.js `24.14.1` and npm `11.17.0`, satisfying the installed development tools' engine requirements. Vite `8.3.5` and Vitest `5.0.5` were verified with this runtime on 27 October 2026. Install the locked dependencies with `npm ci`.

- `src/domain/` contains host-independent domain entities, value objects, and validation.
- `src/application/` coordinates authoring through an explicit project storage port.
- `src/adapters/` contains the in-memory project storage adapter.
- `src/presentation/` contains the React renderer, disposable specimens and independent presentation drafts.
- `test/domain/`, `test/application/`, `test/adapters/` and `test/presentation/` contain tests named `*.test.ts`.

Project module imports use `@domain/…`, `@application/…`, `@adapters/…` and `@presentation/…`; test fixtures use `@tests/…`. TypeScript maps these in `tsconfig.json`; Vite and Vitest share the runtime mappings exported by `vite.config.ts`. The test config's relative import of that Vite configuration is a bootstrap dependency, not an application-module import. Aliases do not change the architectural dependency rules.

Historical review/research manifests retain the paths and import text of their identified snapshots. After the presentation rename and alias refactor, verify those manifests against their original commits rather than rewriting historical evidence to match the current tree.

| Command | Purpose |
|---|---|
| `npm run typecheck` | Check host-independent source/tests, browser/TSX and build-tool types separately |
| `npm test` | Run Vitest once |
| `npm run test:watch` | Run Vitest in watch mode |
| `npm run dev -- --host 127.0.0.1` | Open the session-only browser authoring app |
| `npm run build` | Check both type scopes, then build the browser app |
| `npm run preview` | Preview an existing Vite production build |

All TypeScript configurations enable strict checking. The base configuration includes domain/application/adapters and pure tests, excluding the UI; `tsconfig.presentation.json` adds browser libraries and JSX for presentation and the isolated browser fixture. `tsconfig.tools.json` checks Vite/Vitest configuration with Node types; `@types/node` is a development dependency only. The base configuration excludes browser and Node global types, and the browser configuration does not include Node globals. Dependency declaration checking is skipped because the Vite and Vitest declarations reference host event types that are intentionally absent; project source and tests remain strictly checked. Vitest uses its default Node test environment and explicitly includes `test/**/*.test.ts`; historical isolated prototype tests keep their own package and runner.

Start from an empty page, create a project (including an exact empty name), organize root/nested groups, and create a disclosed opaque-black Color token. Revise exact literals or explicitly replace them with ID-linked references. Apply is explicit; mode switches and passive color-space exploration retain independent drafts. Reloading, closing or leaving loses all project data. No browser persistence or project network service is used. This is not the complete PWA: retention/backup, interchange, install/offline and Electron remain deferred.

Calculated representations are approximate and can be unavailable. Direct canonical Decimal entry and alpha remain exact; Culori `4.0.2` is bounded by the [agreed numerical policy](docs/increments/003-color-policy-proposal.md). No authored gamut mapping or clamping occurs. The known exceptional tiny-red → HSL defect safely returns numerical unavailability with source intact. Mixing, gradients, HEX and a two-dimensional picker are outside this increment.

Build before `npm run preview -- --host 127.0.0.1 --port 4173 --strictPort`. The production entry always starts empty. For acceptance testing only, the development server also serves `http://127.0.0.1:5173/test/browser/fixture.html` (append `?broken=true` for two retained missing references). This explicit test entry injects controlled storage failures, protected metadata and an inspect-only Number; it is excluded from the production build and is not a loader/import API. Its `window.dtwFixture` test controls are documented in [implementation evidence](output/playwright/increment-003-implementation/observations.md).

The [implementation evidence](output/playwright/increment-003-implementation/observations.md) records dependency provenance/licenses, independent numerical fixtures, browser checks and coverage limits. The test reference JSON is copied unchanged from the frozen high-precision CSS Color 4 research fixture; the tests do not use Culori output as their expected oracle.

## In-memory application authoring

`createAuthoringOperations(storage)` in [src/application/authoring.ts](src/application/authoring.ts) accepts the explicit [ProjectStorage port](src/application/project-storage.ts). Supply `new InMemoryProjectStorage()` from [src/adapters/in-memory-project-storage.ts](src/adapters/in-memory-project-storage.ts). Calls are synchronous and sequential with one writer; this port does not define a canonical file schema or a concurrent-write protocol.

- `createProject(input)` creates empty project metadata using a supplied ID.
- `createGroup(input)` creates a root or nested namespace group in the specified project.
- `createColorToken(input)` creates one explicitly typed color token with a structured literal or whole-value reference and one unconditional assignment. Identity, name, parent, and regeneration policy are explicit; layer and semantic role remain optional metadata. No layers or roles are inferred.
- `reviseColorToken({ projectId, tokenId, value })` replaces an existing color token's sole unconditional literal or reference with the complete supplied literal or whole-value reference, including deliberate changes between those forms. All other token data is preserved, including regeneration protection, which permits explicit manual edits. Incomplete, conditional, component-layer, and expression/composite-bearing edited tokens are ineligible. A recognizable broken reference can be repaired only when the replacement clears all candidate namespace/reference diagnostics; unrelated remaining diagnostics block the edit.
- `renameGroup(projectId, groupId, localName)` preserves identities and references while derived paths change.
- `readProject(projectId)` returns project metadata and authored groups/tokens alongside domain-derived path results.
- `inspectToken(projectId, tokenId)` returns authored data, its path result, and a separate domain resolution result with selection, trace, and diagnostics.
- `validateProject(projectId)` returns separate namespace structural and reference diagnostics. It does not establish complete definitions, assignment coverage, resolution success, or name uniqueness.

Operations return `{ status: "ok", value }` or `{ status: "failure", error }`. Expected failures distinguish missing entities, duplicate identities, invalid constructor input, invalid candidate relationships, and storage failures. Modifications check the candidate before committing once; rejected commands leave stored data unchanged. The storage port requires atomic replacement or unchanged state on failure. Unexpected programmer exceptions propagate.

The in-memory adapter copies preloaded fixtures, committed inputs, and loaded outputs so caller mutations cannot alter stored authored data. Preloaded repairable fixtures test existing domain diagnostics; they are not an import/loader API. Normal authoring rejects missing/foreign targets and incompatible declared types, while typed-but-unassigned color targets remain referenceable and resolve to `missing-assignment`.

This enabling workflow has no axes or presets, UI, import/export, durable save/open, or backup. Sibling-name collision checks remain explicitly deferred, so structural success does not guarantee unique paths. [Application workflow tests](test/application/authoring.test.ts) and [repairable-data tests](test/application/repairable-data.test.ts) demonstrate the boundary without selecting a host or persistence format.

## Domain API notes

Reference construction validates the structural field/index path representation and preserves broken references for repair. `validateProjectTokenReferences(projectId, tokens, selection)` reports target existence, project ownership, declared-type compatibility, and unsupported value paths for all authored reference assignments. It also reports ambiguous selected assignments and cycles under the supplied completed project selection. Supply the complete token snapshot and a selection completed from that project's axes. Currently only whole-value references (`valuePath: []`) are supported; non-empty paths remain diagnosable data. This validation does not resolve values or establish assignment coverage for every possible variation selection. Aggregate-local construction and assignment changes must be followed by project validation before accepting authored changes.

`resolveToken(projectId, tokens, tokenId, selection, context?)` resolves one token through selected literals, whole-value aliases, and portable expressions. Each dependency independently selects its most-specific assignment under the same completed project selection. It returns `resolved` with the exact literal, root matched condition, and ordered dependency trace, or `unresolved` with a reason, diagnostic identifying the failing token, and the trace up to failure. It preserves authored data and never falls back after a selected assignment fails. The caller supplies the complete project token snapshot and a selection already completed from that project's axes. Duplicate token identities are rejected with `RangeError`. Iterative traversal supports long alias chains and nested expression evaluation. Inactive and unrelated references remain the responsibility of project validation, which also traverses expression operands and detects selected dependency cycles with multiple outgoing references.

`createExpression` constructs the closed serializable AST for `portable.math.add.v1`, `subtract.v1`, `scale.v1`, `min.v1`, `max.v1`, and `clamp.v1` under the same `portable.math` prefix. It checks operation support and arity; operand compatibility and result types are derived during evaluation with target and context information. Operands may be implemented literals, token references, nested expressions, or an explicit `font.rootSize` context reference. `analyzeExpression` extracts references and explicit context keys without evaluating; mixed-unit requirements may become known only after operand resolution.

Decimal addition, subtraction, and multiplication are exact. Number operations require no context. Same-unit dimensions preserve their unit, and scaling a dimension requires a number scalar. Mixed `px`/`rem` operations require `context["font.rootSize"]` as a non-negative `px` dimension and return `px`; no root size is assumed. Missing required context produces `context-required`. Invalid arity, operands, context, and reversed clamp bounds produce `invalid-expression` with a specific diagnostic code; unknown operations produce `unsupported-expression`. Expression diagnostics carry an operand-index path within the owning token's AST. Expressions remain authored ASTs after evaluation. Composite schemas beyond transition, typography, and shadow, additional context keys, and target-specific operations remain unimplemented.

`TokenGroup` provides stable project-owned identity, an opaque local name, an optional description, and an explicit parent group ID or `null`. `createTokenGroup` constructs the data and `renameTokenGroup` preserves identity and containment. Project relationships are checked separately.

Namespace operations consume a `ProjectNamespaceSnapshot` containing the project ID, groups, and tokens. This is an operation input, not a persistence format or a Project aggregate. `validateProjectNamespace` reports foreign entities, missing or foreign parents, and group ancestry cycles. Duplicate group or token IDs in the snapshot raise `RangeError`. `deriveTokenPath` and `deriveTokenGroupPath` return root-to-leaf name-segment arrays or diagnostics for invalid ancestry. They traverse only the requested ancestry and return no partial path on failure. `moveTokenGroup` and `moveTokenInNamespace` return a new snapshot only after its structural namespace validation passes; inputs and descendant identities remain unchanged. Moving to `null` places the entity at the project root.

Namespace names remain opaque, including whitespace, separators, Unicode, and empty text. Name grammar, normalization, sibling-name collision checks, joined-path formatting, and deletion are deferred. Structurally valid snapshots may therefore still have duplicate derived paths; namespace validation currently does not establish naming validity. Renames and moves change derived paths without rewriting token definitions, references, or descendant containment.

`Project` contains a caller-supplied stable `ProjectId`, an opaque name, and an optional description. `createProject`, `renameProject`, and `changeProjectDescription` construct or return readonly plain data; edits preserve identity without mutating the input. Passing `undefined` to `changeProjectDescription` removes the field, while empty text remains explicit. Workspace location, tokens, groups, settings, provenance, and export configuration remain separate concerns. Identifier generation and name-validation policies remain open.

`createPercentageLiteral(ratio)` constructs `{ kind: "literal", valueType: "percentage", ratio: Decimal }` from canonical ratio text (`"0.5"` represents `50%`). Ratios may be negative or greater than one. Percentage assignments and whole-value aliases resolve without conversion; number/percentage and dimension/percentage substitutions are type errors. Percentage operands and scalars remain invalid in all portable operations. Parsing percentage display strings and references into the `ratio` field are outside the current support boundary.

`createCubicBezierLiteral(controlPoints)` constructs `{ kind: "literal", valueType: "cubicBezier", controlPoints: [x1, y1, x2, y2] }` from exactly four canonical Decimal strings. Both x coordinates must be in `[0, 1]`; y coordinates accept any finite canonical Decimal, including overshoot. Construction copies the coordinates without reordering or clamping. Cubic Bézier assignments and whole-value aliases preserve the coordinates through variation-aware resolution. The current arithmetic operations reject Bézier quantities and scalars. Coordinate references, curve evaluation, easing presets, and CSS parsing remain outside current support.

`createDurationLiteral(value, unit)` constructs `{ kind: "literal", valueType: "duration", value: Decimal, unit: "ms" | "s" }`. `DURATION_UNITS` supplies the runtime unit vocabulary and its derived type. Values use canonical Decimal text and may be positive, negative, fractional, or zero; a lowercase unit is always required. Construction, assignments, and whole-value alias resolution preserve the authored unit without conversion (`"200"`/`"ms"` and `"0.2"`/`"s"` remain distinct representations). Other token types and current arithmetic expression operations do not implicitly accept duration values. Part-value references, conversion operations, and display-string parsing remain deferred. Transition field constraints are defined by the transition composite.

`createTransition({ duration, delay, timingFunction })` constructs the `kind: "composite"`, `valueType: "transition"` value. All fields are required; duration and delay accept duration literals or token references, and timingFunction accepts a cubic Bézier literal or reference. Inline duration must be non-negative; delay remains signed. Construction copies its constituent values and references. Token assignments enforce the `transition` type.

Project reference validation traverses transition fields with their expected types and selected dependency cycles. `resolveToken` follows field references and whole-transition aliases under one completed variation selection and returns a derived `ResolvedTransitionValue` with literal fields. Authored units and references remain unchanged; assignments are never merged by field. Duration sign validation occurs after reference resolution and reports `invalid-composite` / `negative-transition-duration` for a negative result. Missing or wrongly typed loaded fields report `invalid-transition-field`. Diagnostics carry the field and, during resolution, its owning token identity. Part-value paths, field expressions, and using composite values as expression operands remain unsupported.

`createFontWeightLiteral(value)` constructs `{ kind: "literal", valueType: "fontWeight", value: Decimal }` from canonical numeric text in the inclusive range `[1, 1000]`. Fractional values remain exact; comparisons do not use binary floating point. Assignments and whole-value aliases preserve the distinct `fontWeight` type through variation-aware resolution. Ordinary numbers are not implicitly compatible. Named-input parsing, adapter normalization, part-value paths, and font-weight expression operations remain deferred.

`createFontFamilyLiteral(families)` constructs a nonempty ordered stack of `{ kind: "named", name }` and `{ kind: "generic", family }` entries. `GENERIC_FONT_FAMILIES` supplies the initial lowercase `serif`, `sans-serif`, `monospace`, and `system-ui` vocabulary and its derived type. Blank named entries are rejected; accepted names retain their exact text. Construction copies entries and preserves duplicates and fallback order. Named and generic families remain distinct even when their text matches. Assignments and whole-stack aliases preserve the `fontFamily` type through variation-aware resolution. Per-entry references, CSS parsing, font availability checks, adapter mapping, and expression operations remain deferred.

`createTypography({ fontFamily, fontSize, fontWeight, letterSpacing, lineHeight })` constructs the `kind: "composite"`, `valueType: "typography"` value with five explicit literal-or-reference fields. Font size is a dimension, line height a unitless number multiplier, letter spacing a signed dimension, and font family/weight use their foundational literal types. Font size and line height must be non-negative, including after resolving references. Construction copies fields while preserving exact values, dimension units, and font-stack semantics.

Token assignments and whole-typography aliases use the `typography` type. Project validation checks typed field references and selected dependency cycles; resolution derives `ResolvedTypographyValue` with literal fields under one completed variation selection. Failed fields never merge with another assignment or trigger fallback. Sign violations produce `invalid-composite` with `negative-typography-font-size` or `negative-typography-line-height`; malformed loaded fields use `invalid-typography-field`. Diagnostics identify the field and its owning token. Part-value paths, direct field expressions, and whole-composite expression operations remain deferred. A field reference may still target a number or dimension token whose own selected assignment evaluates a supported expression.

`createBooleanLiteral(value)` constructs `{ kind: "literal", valueType: "boolean", value: boolean }` only from an actual boolean. Non-boolean inputs raise `TypeError` without coercion or defaults. Explicit `false` remains authored data through assignments, whole-value aliases, and variation-aware resolution; it is never treated as an absent value or a reason to fall back to another assignment. Other token types are not implicitly compatible. Part-value paths and all current expression operations remain unsupported for boolean values.

`createShadow({ layers })` constructs a `kind: "composite"`, `valueType: "shadow"` value with a non-empty ordered stack of explicit layers. Each layer requires `color`, `offsetX`, `offsetY`, `blur`, `spread`, and `inset` as correctly typed literals or references. Blur must be non-negative, including after resolution; offsets and spread are signed dimensions, and inset is an explicit boolean without defaults. `SHADOW_FIELDS` and `SHADOW_FIELD_TYPES` supply the field vocabulary and expected types. Construction copies the stack and constituents, preserving order, duplicates, exact color data, authored dimension units, and explicit false.

Assignments and whole-stack aliases resolve under one completed variation selection to `ResolvedShadowValue`. Project reference validation checks all authored field references; selected dependencies determine cycle detection and resolution. Failures do not merge layers or trigger fallback. Field diagnostics carry a zero-based `layerIndex` and field, with `fieldOwnerId` during resolution. Invalid stacks or fields report `invalid-composite` with `invalid-shadow-layers` or `invalid-shadow-field`; negative blur reports `negative-shadow-blur`. References to whole layers or stacks inside another stack, part-value paths, direct field expressions, CSS parsing, and shadow expression operations remain deferred. A dimension field reference may target a token whose own assignment evaluates a supported expression. This canonical stack does not select DTCG import/export mappings.
